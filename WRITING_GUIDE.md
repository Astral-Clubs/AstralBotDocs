# Руководство по написанию документации

Это правила для всех, кто пишет или правит страницы [docs.astralbs.xyz](https://docs.astralbs.xyz). Они нужны, чтобы документация читалась как написанная одним автором и чтобы читатель без опыта программирования всегда находил ответ.

Если вы впервые открываете проект, начните с [CONTRIBUTING.md](CONTRIBUTING.md): там описано, как предложить правку. Здесь описано, как писать сами тексты.

## Для кого мы пишем

Основной читатель — администратор Telegram-чата. Он не программист, пришел за конкретным результатом («хочу, чтобы бот здоровался по имени») и читает страницу ровно столько, сколько нужно, чтобы это получить.

Из этого следует:

- Сначала результат, потом объяснение. Покажите готовый пример, затем разберите, как он устроен.
- Один шаг — одно действие. Не объединяйте в предложение три настройки.
- Термин объясняется при первом упоминании на странице или ссылкой на [словарик](docs/glossary.md).
- Продвинутый материал (синтаксис, типы, ограничения движка) живет в разделах `templates/advanced` и `reference`. Страницы для новичков на него только ссылаются.

## Тон и язык

- Пишем по-русски, обращаемся на «вы». Без «давайте», «а теперь», шуток и восклицательных знаков.
- Короткие предложения. Активный залог: «Бот отправит сообщение», а не «Сообщение будет отправлено ботом».
- Не пишем «просто», «легко», «очевидно». Если читателю не получилось, эти слова обижают.
- Кавычки-елочки «так», тире длинное — вот так. Неразрывный пробел не нужен.
- Названия кнопок, полей и пунктов меню интерфейса выделяем **жирным** и берем в точности как в интерфейсе: **«Сохранить»**.
- Код, команды, переменные и значения — в обратных кавычках: `member.name`, `/start`.
- Числа и единицы: «10 секунд», «5 минут», «до 4096 символов». Диапазоны через тире: «от 1 до 5» или «1–5».

## Типы страниц

У каждой страницы одна цель. Не смешивайте типы.

| Тип | Цель | Где лежит | Как выглядит |
|---|---|---|---|
| Руководство | Привести читателя к результату по шагам | `templates/beginners`, `commands` | Вводный абзац, пример, шаги, частые ошибки |
| Справочник | Дать точные факты для поиска | `reference`, `templates/advanced` | Таблицы свойств и параметров, без «воды» |
| Пример | Показать готовое решение для копирования | `templates/examples.md` | Задача, готовый шаблон, превью результата |
| Объяснение | Рассказать, как это устроено и почему | `templates/places.md`, `templates/shared.md` | Связный текст с короткими разделами |

## Анатомия страницы

Каждая страница начинается одинаково:

```md
---
description: Одно-два предложения: о чем страница. Попадает в поиск, превью ссылок и llms.txt.
---

# Заголовок страницы

<p class="lead">Вводный абзац: что здесь найдет читатель и когда это нужно.</p>

## Первый раздел { #first-section }

Текст раздела.
```

Правила, которые проверяет `bun run check` (при нарушении CI не пройдет):

- Во frontmatter есть `description` длиной от 30 до 320 символов.
- На странице ровно один заголовок первого уровня `# `.
- У каждого заголовка второго уровня `##` есть латинский якорь `{ #like-this }`: строчные латинские буквы, цифры и дефисы. Якорь не меняется после публикации, потому что на него ссылаются из других мест.
- Якоря на странице не повторяются.
- Имя файла — латинские строчные буквы, цифры и дефисы: `first-command.md`, не `Первая команда.md` и не `first_command.md`.
- Внутренние ссылки пишутся без расширения `.md`.
- В тексте нет `TODO`, `FIXME` и заглушек.
- Каждая страница есть в боковом меню `docs/.vitepress/sidebar.ts` или в шапке сайта.
- Теги `<TgPreview>` парные.

Заголовки третьего уровня `###` якоря не требуют. Глубже третьего уровня не уходим.

## Заголовки

- Заголовок называет содержание, а не жанр: «Кнопки под сообщением», а не «Работа с кнопками».
- Для руководств допустим глагол или вопрос: «Как добавить кнопку», «Что делать, если шаблон не сохраняется».
- Без точки на конце, без двоеточий, без номера («1. Введение» не нужно, порядок задает меню).

## Ссылки

- Между страницами проекта — относительные, без `.md`: `[Где используются шаблоны](../places)`, `[Условия](./conditions)`.
- На раздел другой страницы — через якорь: `[квоты](../advanced/limits#quotas)`.
- Внешние ссылки — полным адресом с `https://`. Они проверяются раз в неделю, поэтому не ссылайтесь на нестабильные источники.
- Текст ссылки описывает цель: «читайте о [частых ошибках](./mistakes)», а не «нажмите [здесь](./mistakes)».
- Закрытых для читателя адресов (внутренние репозитории, закрытые чаты, личные заметки) в документации быть не должно.

## Таблицы

Таблицы — главный инструмент справочников.

```md
| Свойство | Тип | Описание |
|---|---|---|
| `id` | Число | ID пользователя в Telegram |
| `name` | Строка | Имя и фамилия |
```

- Первый столбец — то, что ищут: имя переменной, свойства, параметра.
- Вертикальная черта внутри ячейки экранируется: `` `x \| length` ``.
- Таблица шире четырех столбцов — признак того, что ее нужно разбить.

## Код и шаблоны

Примеры шаблонов пишутся в блоках с языком `template`. У него своя подсветка для `{{ }}`, `{% %}` и `{# #}`:

````md
```template
Привет, {{ member.firstName }}!
{% if member.warnCount > 0 %}У вас предупреждений: {{ member.warnCount }}.{% endif %}
```
````

Другой текст (вывод, структура папок) — блок `text`. Блок без языка не используйте.

Правила для примеров:

- Пример рабочий. Перед публикацией вставьте его в редактор шаблонов бота и проверьте результат. «Написано по памяти» — самая частая причина ошибок в документации.
- Пример минимальный: ничего лишнего, что отвлекает от темы страницы.
- Если пример нужно адаптировать, места для замены выделите понятными словами: `{{ chat.title }}`, а не `{{ x }}`.

### Опасные места Markdown и Vue

VitePress превращает страницу в Vue-компонент, поэтому есть два подводных камня.

- `{{ ... }}` в обычном тексте Vue примет за свою вставку и упадет. Такие записи пишите только `` `в обратных кавычках` `` или в блоке кода. Весь инлайн-код на сайте уже защищен автоматически.
- Угловые скобки в обычном тексте (`<имя>`) Markdown воспримет как HTML-тег. Пишите `` `<имя>` `` в кавычках кода.

## Подсказки

Контейнеры выделяют то, что нельзя пропустить. Не злоупотребляйте: если на странице больше трех подсказок, часть из них, вероятно, обычный текст.

```md
::: tip Совет
Полезное, но не обязательное.
:::

::: info Информация
Нейтральный контекст: чем отличаются два режима, где еще это применяется.
:::

::: warning Внимание
Из-за этого можно получить не тот результат.
:::

::: danger Осторожно
Действие необратимо или ломает работу бота.
:::

::: details Подробнее
Скрытый по умолчанию материал для любопытных.
:::
```

## Превью сообщения Telegram

Чтобы показать, как выглядит результат шаблона, используйте компонент `TgPreview`. Он рисует сообщение как в Telegram, с кнопками и реакциями.

```md
<TgPreview user="!кубик" user-name="Анна" :buttons="[['🎲 Еще|primary', 'Сайт|link']]">

🎲 [Анна](#) бросает кубик… выпало **4**!

</TgPreview>
```

| Атрибут | Что делает |
|---|---|
| `user` | Сообщение участника над ответом бота |
| `user-name` | Имя участника, по умолчанию «Вы» |
| `:buttons` | Ряды кнопок. Стиль после `\|`: `primary`, `success`, `danger`, `link`, `copy`, `disabled` |
| `reaction` | Реакция под сообщением |
| `ephemeral` | Пометка «видно только вам» |
| `label` | Подпись над превью |

Правила:

- Внутри превью обычный Markdown. Пустые строки после открывающего и перед закрывающим тегом обязательны.
- Заголовки внутри превью не попадают в оглавление и поиск.
- Спойлер: `<span class="tg-spoiler">…</span>`.
- Превью показывает то, что бот отправит в самом деле. Если на боте результат другой, правьте пример, а не превью.
- Сразу после превью обычно идет блок `template` с кодом, который его создает, или наоборот.

## Шаги и карточки

Пошаговая инструкция оформляется блоком `steps`. Каждый шаг — заголовок третьего уровня:

```md
<div class="steps">

### Первый шаг
Текст шага.

### Второй шаг
Текст шага.

</div>
```

Карточки-ссылки для обзорных страниц:

```html
<div class="cards">
  <a class="card" href="/commands/">
    <span class="card-title">Заголовок</span>
    <span class="card-text">Описание.</span>
  </a>
</div>
```

## Метки

Новые возможности помечаются бейджем: `<Badge type="tip" text="новое" />`. Ставьте его рядом с названием свойства, функции или раздела. Бейдж `warning` — для того, что скоро изменится или работает с оговорками, `info` — для справочных пометок.

Бейдж «новое» не вечный. Мейнтейнеры убирают его после нескольких релизов бота, чтобы он не терял смысл.

## Устаревание и точность

Документация должна совпадать с ботом. Поэтому:

- Если поведение бота меняется, в том же PR или сразу после правятся страницы `templates/advanced/*` и `reference/*`: они первоисточник для остальных.
- Если вы не уверены в поведении, не угадывайте. Откройте задачу и опишите, что именно не удалось проверить.
- Скриншотов в документации нет: они устаревают быстрее текста. Используйте `TgPreview` и описания интерфейса.

## Доступность

- Каждое изображение (если оно все-таки нужно) имеет осмысленный `alt`.
- Не передавайте смысл только цветом: «красная кнопка» дополняйте названием.
- Не используйте эмодзи вместо слов. В превью сообщений они допустимы, потому что воспроизводят настоящий результат.

## Добавление страницы

1. Создайте файл `.md` в подходящей папке (имя — латиницей, через дефис).
2. Добавьте `description`, заголовок, вводный абзац.
3. Добавьте страницу в `docs/.vitepress/sidebar.ts`. Если страница важная и должна быть в шапке, добавьте ее в `nav` в `docs/.vitepress/config.mts`.
4. Запустите `bun run verify`. Он проверит страницы, прогонит тесты и соберет сайт: сборка падает на битой внутренней ссылке.
5. Откройте страницу в `bun run dev` и проверьте ее глазами, особенно на узком экране.

## Чек-лист перед pull request

- [ ] Страница отвечает на один вопрос читателя
- [ ] Есть `description`, один `# `, у `##` есть якоря
- [ ] Все примеры проверены на боте
- [ ] Нет «просто», «легко», «очевидно»
- [ ] Ссылки относительные и без `.md`
- [ ] Страница добавлена в меню
- [ ] `bun run verify` проходит
